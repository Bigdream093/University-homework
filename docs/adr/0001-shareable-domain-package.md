# ADR 0001：将共享业务规则放入独立 workspace 包

- 状态：已采纳
- 日期：2026-10-18

## 背景

应用的浏览器端（`web`）和 Express 服务端（`server`）都需要执行一部分相同的业务规则，例如成绩计算、必答题序列化与校验、文件约束、提交文件名规范化和提交统计。若两端各自维护实现，规则容易逐渐不一致；若浏览器直接导入 `server/src`，又会把服务端实现边界带入浏览器代码。

## 决策

把两端共同使用、可在浏览器和 Node.js 中运行的纯 JavaScript 规则放在 `packages/domain`，以 `@university-homework/domain` 作为 npm workspace 私有包。包通过 `exports` 显式列出可用模块；`web` 与 `server` 都从这些公开入口导入同一实现。

该包只承载不依赖 HTTP、数据库、文件系统或 UI 框架的规则与数据变换。认证、持久化、请求处理、文件系统边界等运行时职责仍由服务端负责；界面交互仍由前端负责。

## 依据

- 根目录 `package.json` 将 `packages/domain`、`web` 和 `server` 纳入同一 workspace，且两端都声明了对该包的依赖。
- `packages/domain/package.json` 使用 ESM，并通过显式 `exports` 暴露各模块。
- 两端分别导入成绩、必答题、文件约束、提交摘要等共享模块，说明这些规则需要保持同一口径。
- `scripts/check-shared-boundary.cjs` 检查浏览器运行时代码不得直接导入 `server/src`，维护前端与服务端的依赖边界。
- 根目录测试流程分别运行共享包 lint、服务端测试和前端测试，使同一共享实现由两侧共同验证。

## 后果

- 共享规则只有一个实现来源，可降低前后端校验和计算口径漂移。
- 共享模块必须保持浏览器与 Node.js 兼容，并通过包的公开导出路径访问。
- 需要服务端能力的逻辑不能仅因与业务有关就放入此包；调用数据库、文件系统或 HTTP 的代码应留在相应运行时层。
- 该包目前是仓库内部的 workspace 包，不单独发布，也不需要独立构建产物。
